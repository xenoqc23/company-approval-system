# 경리 결제 등록 방식 로컬 테스트 검증

대상: `xenosys-local-payment-20261023.zip`. 실제 NAS에 접속하거나 배포하지 않았다.

## 확인 결과

- SQLite 통합 66건 통과. 새 결제 흐름 14건을 포함하며, 마지막 기본 탭 선택 변경 후 해당 14건을 다시 통과했다.
- MariaDB 10.11 통합·동시 처리 80건 통과. 중복 결제 완료와 결제 완료·반려 경쟁에서 한 번만 처리되는 것을 확인했다.
- 기존 workflow 319건 중 298건 통과, 환경별 21건 건너뜀. 휴가원·연차 등 기존 사내결재 기능을 유지한다.
- 전체 소스·자산·NAS 도구·실행기·해시·초기화 범위 패키징 검사 4건 통과.
- Django check, 미반영 migration 검사, Python compileall, 구매 JS 문법 및 git diff 공백 검사 통과.
- purchasing 0009에서 0010으로 올린 가상 기존 DB에서 모든 기존 테이블의 기존 열 값을 비교해 보존을 확인했다. 6개 과거 요청은 payment_tracking=False로 원래 결재 방식을 유지하며, 권한 자동 부여는 없다.

## 실제 ZIP 설치 및 브라우저

ZIP을 새 폴더에 풀어 migration·가상 직원 생성·시스템 검사를 수행했다. 설치 직후 가상 직원 12명·문서 0건이며 v4 데이터·쿠키로 분리됨을 확인했다. 테스트용 Python 가상환경만 실행 환경에 연결했고, 그 환경이나 생성된 DB는 ZIP에 포함하지 않았다.

압축 해제본에서 Chromium으로 아래 항목을 확인했다.

1. 구매 링크가 기본 화면에 표시되고 제출 시 필수다.
2. 검토자 부서·승인자 선택란이 펼쳐져 있고 승인 요청이 주요 버튼이다. 승인완료는 권한이 있는 검토자의 보조 버튼이다.
3. 검토자 전달·지정 검토자의 내부 승인완료와 개발팀/그 외 부서의 담당 이사 구매확인 경로.
4. 경리의 품목 취합과 대표 결제 요청.
5. 대표의 기안자·품목·구매처·수량·가격·용도·진행상황 조회. 처리 버튼·수령 집계·새 요청의 미결 건수는 없다. 위조한 대표 처리 POST도 403으로 차단된다.
6. 선택 품목만 결제 완료, 다른 품목은 결제 대기로 유지. 품목별 반려·보류와 필수 사유.
7. 기안자에게 최종결재완료 안내. 수령 완료 이후 경리의 완료 탭에 반영.
8. 결제 전 금액 변경 → 기존 금액 보존 → 변경 금액으로 새 요청 → 결제 완료.
9. 미수령 결제 등록 정정 → 결제 대기로 복구 → 다시 완료 등록.
10. 기존 직원·규정 화면과 320·390·768·1440·2560px 화면. 페이지 가로 넘침과 JavaScript 실행 오류가 없다.

재현 스크립트: `packaging/check_payment_local.py`. 별도의 새 가상 seed_full_demo 환경, loopback 주소, 테스트 비밀번호 파일이 필요하다. 실제 계정·운영 DB에는 사용하지 않는다.

## 적용 범위와 제한

- Python·Django·Chromium·MariaDB 실행 검증은 Linux에서 수행했다. Windows BAT의 명령과 CRLF는 검사했지만 실제 Windows PC 실행은 직접 검증하지 않았다.
- 실행하려는 PC에는 Python 3.10 이상이 필요하다. 첫 설치에는 의존 패키지를 내려받을 수 있어야 한다.
- 실제 은행 이체·카드 결제 자동화는 포함하지 않는다. 경리는 실제 결제 사실을 전달받은 뒤 완료를 등록한다.
- 예시 화면과 테스트 데이터는 전부 가상이다. 개인 정보·운영 DB·비밀번호·키·.env는 배포하지 않는다.
