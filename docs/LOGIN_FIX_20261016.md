# 로그아웃 후 재로그인 CSRF 오류 보완

NAS 모바일 업데이트 후 일반 창에서 PC·휴대폰 모두 CSRF 403이 발생했다. 새 시크릿 창과 사이트 데이터 삭제 직후에는 로그인됐지만, 사용자는 로그아웃 후 다시 로그인하면 오류가 반복된다고 확인했다. `.env`의 접속 호스트·신뢰 Origin·보안 쿠키·HTTPS 리디렉션·프록시 신뢰 값은 기존 HTTPS 설정과 일치했다.

이 환경에서 NAS에 직접 접속하거나 공개 URL을 통해 진단할 수 없었다. 따라서 운영 요청의 정확한 CSRF 거절 사유를 확정한 것은 아니다. 기존 코드에서 확인한 것은 Django 기본 `sessionid`·`csrftoken` 이름을 공유하고, 로그인 및 동적 화면의 캐시를 금지하지 않았다는 점이다. 기본 이름의 쿠키가 다른 앱에 의해 덮어써지거나, 다른 탭의 로그인으로 토큰이 회전한 뒤 이전 로그인 폼을 제출하면 동일한 403을 재현했다. 반면 독립된 서버에서 최신 폼만 이용하는 단순 로그인/로그아웃 반복은 수정 전에도 통과했다.

## 변경

- 쿠키 이름을 `xenosys_approval_sessionid`와 `xenosys_approval_csrftoken`으로 분리한다. 쿠키는 포트로 분리되지 않으므로 같은 NAS 호스트의 다른 Django 앱과 기본 이름을 공유하지 않는다. 기존 HTTPS·HttpOnly·SameSite 설정은 유지한다.
- 로그인/로그아웃 응답과 공통 동적 HTML에 `private, no-store, no-cache`를 지정한다.
- 로그인 직전에 동일 출처의 읽기 전용 `GET /login/csrf/`에서 최신 토큰을 받은 후 정상 POST한다. 오래된 탭에서도 현재 쿠키와 맞는 토큰을 사용한다. 갱신 실패 시 자격 증명을 제출하지 않고 재시도할 수 있게 한다.
- JavaScript 없이도 새 로그인 화면의 기본 GET/POST 흐름을 유지한다. CSRF 검사, 신뢰 Origin, 권한·가입 승인·필수 비밀번호 변경 검사를 우회하지 않는다. 실패한 POST를 자동 재실행하지 않는다.
- 로그인 아이디 입력의 자동 대문자 변환·맞춤법 수정을 끈다. 계정의 대소문자 처리나 비밀번호 규칙은 변경하지 않는다.
- 실제 운영에서 오류가 남으면 사유를 확인할 수 있도록 Django의 CSRF 거절 사유를 콘솔에 기록한다. 표준 로그에는 사유와 URL 경로만 포함되며 비밀번호·토큰 값은 기록하지 않는다.

쿠키 이름 변경으로 기존 로그인은 한 번 해제된다. 사용자 계정·비밀번호·권한·문서·연차 계산·DB 스키마 및 `.env`는 교체하지 않는다.

## 검증

1. 새 회귀 시험 9건을 포함해 Django 시험 133건 실행: 129건 통과, MariaDB 전용 4건 건너뜀. HTTPS·프록시 헤더, 반복 로그인/로그아웃, 외부 앱 기본 쿠키, 오래된 폼, 갱신 경로의 읽기 전용 동작, 틀린 비밀번호 및 가입/비밀번호 변경 게이트를 확인했다. 잘못된 Origin·토큰 누락·오래된 토큰 직접 POST는 여전히 403이다.
2. Linux Chromium 390px·1366px에서 11개 시나리오 통과: 4회 반복 로그인/로그아웃, 다른 탭에서 토큰 회전 후 이전 폼 제출, 기본 쿠키 충돌, 토큰 조회 통신 실패 후 재시도, 방문 기록 이동 후 새 로그인, JavaScript 없는 기본 폼 3회 반복. JavaScript 예외 없음. `DEBUG=0` 및 NAS와 같은 WhiteNoise 압축·해시 정적 파일 처리를 사용했다.
3. NAS 적용 파일 시험 4건 통과: 허용된 파일만 복사, 이전 파일 백업 및 `.env` 보존, 손상 업로드 거부, 복구/설치 상태 검사. 실제 NAS 대신 임시 가짜 설치에서 실행했다.

[브라우저 검증 결과](ui-verification/auth-login-browser-report.json)

실제 NAS 적용 후의 PC·휴대폰 재로그인, Safari 및 실제 기기 검증은 사용자 확인이 필요하다.

## NAS 적용

[로그인 수정 ZIP](../releases/xenosys-login-fix-20261016.zip)을 File Station의 `/docker/company-approval`에 올려 **여기에 압축 풀기**를 실행한다. 기존 설치나 데이터 폴더는 삭제하지 않는다.

Windows PowerShell에서:

```powershell
ssh -t admin@192.168.1.46 "sudo sh /volume1/docker/company-approval/xenosys-login-fix-20261016/APPLY_LOGIN_FIX.sh"
```

체크섬 확인과 소스 백업 후 기존 `nas.sh update`를 사용해 DB 백업·이미지 빌드·재시작을 수행한다. 잠시 웹 접속이 중단된다. `.login-fix-backup.*`에 이전 파일을 보관하며 `LOGIN_FIX_READY`가 완료 표시다.

첫 확인은 기존 로그인 페이지의 캐시를 피하도록 아래 주소를 새 탭에서 연다.

`https://xenonas.synology.me:18443/login/?v=20261016authfix1`

일반 창에서 로그인→로그아웃→로그인을 두 번 이상 반복하고 PC·휴대폰을 모두 확인한다. 계정 비밀번호를 여기 공유하거나 CSRF 검사를 끄지 않는다.

## 개발 재현

분리된 `seed_demo` 데이터와 Playwright가 설치된 로컬 개발 환경을 사용한다. 시험용 계정의 비밀번호는 `mobile-ui-test-only`이며 운영 계정에 사용하지 않는다.

```sh
APPROVAL_DATA_DIR=/tmp/approval-auth-tests .venv/bin/python manage.py test workflow --noinput
.venv/bin/python packaging/check_auth_login.py --base-url http://127.0.0.1:18085
python3 packaging/test_login_fix_patch.py
python3 packaging/build_login_fix_patch.py
```

브라우저 도구는 localhost/127.0.0.1만 허용한다. 실제 시험은 별도 SQLite DB와 `DEBUG=0`, `CompressedManifestStaticFilesStorage`, WhiteNoise 미들웨어를 사용한 임시 설정 모듈로 수행했다. 운영 NAS나 실제 직원 계정은 시험에서 사용하지 않았다.
