# NAS 운영 배포 준비 계획

작성일: 2026-10-15. 현재는 준비·검토 단계이다. 사용자 요청에 따라 Docker 설정, 운영 코드, NAS, MariaDB, 실제 계정·데이터는 변경하지 않았다.

## 현재 상태

PC 검토본은 Python/Django와 SQLite로 동작하며 기능 시험 111건이 통과했다. MariaDB 연결용 환경변수 분기는 있지만 실제 NAS 연결·MariaDB 동시 처리·운영 서버·운영 백업은 아직 검증하지 않았다. 저장소에는 운영용 Dockerfile/Compose와 Gunicorn 의존성이 준비되어 있지 않다. 이번 문서는 배포 구현이 완료됐다는 의미가 아니다.

## 먼저 확인할 정보

| 확인 정보 | 현재 상태 |
| --- | --- |
| NAS 제조사·모델·OS 버전·CPU 구조·여유 메모리 | 사용자 확인 대기 |
| Docker/Container Manager 지원 여부 | 사용자 확인 대기 |
| MariaDB 설치 위치·버전·내부 연결 방식 | 사용자 확인 대기. 사용자는 NAS에 MariaDB를 구축한 경험이 있음 |
| 사내 접속 주소·내부 DNS·HTTPS 구성 | NAS 정보 확인 후 결정. 우선 사내망 접속을 기준으로 준비 |
| 운영 데이터 시작 방법 | 사용자 확인 대기: 샘플 제외 신규 시작 또는 확인된 PC 자료 이전 |
| 업무 종료 시각·백업 저장 위치·별도 사본 위치 | 기존 보관 기준을 바탕으로 확정 필요 |

비밀번호와 비밀키를 대화에 적거나 저장소에 넣지 않는다. 실제 연결 단계에서 NAS의 환경변수·보안 설정에 입력한다.

## 추천 구성

Docker를 지원하는 NAS라면 ‘직원 PC 브라우저 → NAS의 HTTPS 역방향 프록시 → Django 운영 서버(Gunicorn) → MariaDB’ 구성을 우선 검토한다. 이미 운영 중인 MariaDB를 사용할 수 있으며, 애플리케이션 전용 DB와 전용 DB 계정을 분리한다. 기존 DB나 NAS 서비스를 덮어쓰거나 새 MariaDB를 무조건 중복 설치하지 않는다.

Docker 지원이 없거나 자원이 부족하면 NAS에서 지원하는 Python 서비스 운영 방식 또는 별도 사내 서버를 검토한다. NAS 사양을 확인하기 전 이미지·명령어를 확정하지 않는다.

운영에서는 NAS가 서버 역할을 하므로 직원 PC마다 Python이나 setup/run을 설치하지 않고 사내 접속 주소로 사용한다. 현재 setup.bat/run.bat은 PC 검토용이며 NAS 운영 배포 명령으로 사용하지 않는다.

| 단계 | 준비 및 수행할 내용 | 완료 확인 |
| --- | --- | --- |
| 1. 문구·운영 규칙 정리 | 운영 문구 검토안 반영, 로그인 예시 계정 안내 제거, 미정 전결규정과 최종 업무 기준 확인 | 직원 화면과 관리자 화면을 구분해 검토 |
| 2. NAS 구성 확정 | 장비·Docker·MariaDB·접속 주소·볼륨·포트와 권한 확인 | 기존 NAS 서비스와 충돌 없는 구성표 |
| 3. 배포 파일 준비 | 지원 CPU용 이미지, 운영 WSGI 서버, 정적 파일 처리, 재시작 정책·로그·환경변수 설정 준비 | 별도 시험 환경에서 빌드·시작·재시작 확인 |
| 4. 운영 설정 보완 | 실제 SECRET_KEY, DEBUG=0, 허용 호스트, HTTPS 프록시·CSRF 신뢰 출처·보안 쿠키 설정 | 배포 점검 통과 및 프록시 경유 로그인/POST 검증 |
| 5. MariaDB 시험 연결 | 프로젝트 전용 DB/계정, 문자셋·호환 버전, 마이그레이션과 초기 운영 데이터 준비 | 실제 MariaDB에서 결재·연차·취소·동시 처리 검증 |
| 6. 백업·복구 연결 | DB 논리 백업, 예약·보관·NAS 외부 사본·복구 절차·실패 확인 연결 | 별도 시험 DB에 복원해 수치와 결재 기록 비교 |
| 7. 직원 시범 운영 | 경리·관리자·일반 직원의 실제 PC 여러 대에서 로그인·권한·알림·Excel·일정 확인 | 담당자 확인과 발견 사항 보완 |
| 8. 운영 전환 | 시작 데이터 최종 확인, 전환 전 백업, 실제 계정·규정 설정, 접속 주소 안내 | 운영 점검표와 되돌리기 기준 확인 |

## 현재 소스에서 필요한 배포 작업

- Django 개발 서버 대신 운영 WSGI 서버와 정적 파일 제공을 구성한다. 현재 의존성 파일에는 Gunicorn이 없다.
- 현재 설정에는 DB 접속과 DEBUG/ALLOWED_HOSTS 환경변수 분기가 있다. HTTPS 프록시 신뢰·CSRF 신뢰 출처·보안 쿠키 등은 배포 구성에 맞춰 추가해야 한다. 프록시 헤더는 실제 신뢰할 프록시 구성에 맞춰 설정한다.
- Django 5.2에서 지원하는 MariaDB 버전인지 확인하고 드라이버를 고정·검증한다. 현재 MariaDB 드라이버는 버전 범위만 지정되어 있다.
- 컨테이너 내부의 127.0.0.1은 컨테이너 자신이다. DB가 NAS에 설치되어 있으면 실제 접근 가능한 NAS 주소·포트 또는 컨테이너 네트워크의 서비스 이름을 사용하도록 구성한다.
- 운영 DB 준비 과정에서는 seed_demo를 실행하지 않는다. 현재 PC 설치 도우미는 빈 DB에 가상 계정과 문서를 만들므로 그대로 운영 초기화에 사용하지 않는다. 실제 관리자만 생성하는 초기화 경로와 첫 로그인 비밀번호 변경을 준비한다.
- 계정과 문서를 이전한다면 SQLite 파일을 MariaDB 데이터 폴더로 복사하지 않는다. 자료 선별·키/관계/초기 규정 중복 검사를 포함한 이전 절차를 별도 시험 DB에서 검증한다. 원본 PC DB는 보관한다.
- 현재 백업·복구 기능은 SQLite 전용이다. MariaDB 백업 경로·예약 작업·관리자 화면의 실제 동작을 함께 준비하고 검증한다. 운영 백업이 없는 상태를 완료로 표시하지 않는다.
- 연차 갱신 명령 sync_annual_grants를 NAS 스케줄러에서 반복 실행하도록 구성한다. 현재 접속 시 보완 산정은 있으나, 접속 여부와 무관한 연초 자동 운영은 예약 작업으로 확인한다.

## 데이터·계정 시작안

신규 시작은 샘플 계정·문서를 제외하고 실제 관리자, 회사 규정, 직원 가입 승인, 부서·직급·입사일·기초 연차를 설정하는 방식이다. 현재 비밀번호 길이·본인 승인 등 사용자 확정 정책은 배포 준비만으로 임의 변경하지 않는다. 운영 관리자 초기 비밀번호는 별도로 설정하고 첫 로그인에 변경한다.

PC 자료 이전을 선택하면 실제로 유지할 자료와 시험 자료를 먼저 구분하고 이전 전후 직원 수·문서 수·연도별 총/사용/잔여 연차·공용연차 차감·승인 취소 복원을 비교한다. 삭제 또는 초기화는 대상과 보관 사본을 확인한 뒤 수행한다. 이번 준비에서는 어떤 자료도 삭제하지 않았다.

## 백업 운영안

기존 합의대로 매일 백업 30개·월간 백업 12개와 NAS 외부 사본을 기본으로 한다. 실제 예약 시각과 보관 경로는 환경 확인 후 정한다. 백업 파일 생성뿐 아니라 시험 DB 복원, 최근 백업 유무·실패 확인, 서비스 중지/점검/재시작 절차를 검증한다. 운영 전환 때에는 직전 버전과 DB 백업을 함께 보관하고 스키마가 바뀐 경우 코드만 이전 버전으로 바꾸지 않는다.

## 운영 전환 전에 확인할 보류 사항

- 100만원 초과 전결규정 및 적격 승인자가 없을 때의 별도 예외 처리 방식.
- 비활성 예시 상태인 10만원 초과~100만원 이하 규정의 실제 사용 여부와 허용 직급.
- 실제 회사 규정, 직원 입사일·기초 연차, 관리자와 경리 권한 및 실제 접속 주소.
- 같은 문서의 승인 동시 요청·같은 직원 휴가 동시 제출·여러 직원 연차 변경을 MariaDB에서 시험한 결과.
