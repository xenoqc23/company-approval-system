# 사내결재 시스템 NAS 업데이트 · 2026-10-26

기존 사내결재 시스템에 구매요청 기능과 공통 개선사항을 통합하는 전체 업데이트입니다. 이 안내는 기존 전용 Docker 설치(`/volume1/docker/company-approval`, 프로젝트 `xenosys_approval`) 기준입니다. 현재 운영 버전·계정은 NAS에서 사전 점검합니다. 다른 경로·프로젝트로 설치했다면 기존 값을 확인해 `APPROVAL_BASE`, `APPROVAL_PROJECT`를 그대로 지정하세요.

## 변경 내용

- 지정된 구매확인 담당자가 내부 승인까지 담당하면 구매확인도 함께 처리해 구매 담당자에게 전달합니다. 과거 요청의 ‘함께 확인’ 설정이 꺼져 있어도 적용됩니다. 다른 담당 이사의 승인이나 기안자 본인 승인은 이 조건에 해당하지 않습니다.
- 대표 구매 진행현황은 **진행 중 / 완료**로 구분합니다. 결제 완료·반려된 요청은 완료에서 확인합니다. 처리할 품목이나 보류가 남으면 진행 중에 유지합니다. 다른 요청으로 다시 제출한 보류 품목은 원래 요청의 처리 대상에서 제외합니다. 수령 여부는 이 분류에 영향을 주지 않습니다.
- 대표에게는 새 구매요청 표시와 품목·기안자·구매처·수량·가격·용도를 제공합니다. 대표 승인 버튼 추가는 보류 상태입니다. 실제 결제 후 구매 담당자가 결제 완료·반려·보류를 등록합니다.
- 아이디 저장과 브라우저 비밀번호 자동입력을 지원합니다. 처음 로그인 후 Chrome/Edge의 비밀번호 저장을 선택하세요. 앱은 암호를 별도로 저장하지 않으며 로그인 유지 정책은 바꾸지 않습니다.
- 구매 규정·화면·알림의 업무 담당자 용어를 정리했습니다. 기존 결재·연차·문서 이력과 내부 상태 코드는 보존합니다.

## 적용 전

1. ZIP을 **기존 app·data·backups·.env에 덮어쓰지 말고**, 다음처럼 별도 폴더에 풉니다.
   `/volume1/docker/company-approval/updates/xenosys-nas-purchase-update-20261026-v1/`
2. 회사에서 정한 네 담당자의 **기존 직원 계정**이 등록돼 있어야 합니다. 구매확인자는 개발팀 이사 / 생산팀 이사, 구매 담당자는 활성·가입 승인된 직원, 대표는 이미 회사 대표로 지정된 계정이어야 합니다. 부서·직급·대표 지정·암호를 업데이트가 임의 변경하지 않습니다.
3. 동명이인이면 이름 대신 `username:실제아이디`를 사용합니다. 시스템 관리자가 `admin` 이외의 아이디면 `--operator 실제관리자아이디`를 사용합니다. 아래 예시의 꺾쇠괄호 문구는 실제 값으로 바꾸세요.
4. 사전 점검은 서비스가 실행 중인 상태에서 할 수 있습니다. 실제 업데이트는 업무 입력이 없는 시간에 진행하고 예약 작업도 겹치지 않게 하세요. 기존 백업을 NAS 밖에도 별도 보관하세요.

```sh
cd /volume1/docker/company-approval/updates/xenosys-nas-purchase-update-20261026-v1
sudo sh UPDATE_NAS.sh precheck \
  --development-checker '<개발팀 구매확인자 이름 또는 username:아이디>' \
  --other-checker '<그 외 부서 구매확인자 이름 또는 username:아이디>' \
  --purchaser '<구매 담당자 이름 또는 username:아이디>' \
  --representative '<대표 이름 또는 username:아이디>' \
  --operator admin
```

계정이 없거나 중복되면 사전 점검에서 중단합니다. 기존 문서에서 기안자가 본인의 검토자·승인자로 배정돼 있으면 해당 문서 ID를 표시하고 중단합니다. 기존 담당자 변경 절차로 정리한 뒤 다시 점검하세요. 진행 문서의 담당자·이력을 자동 교체하지 않습니다. 이미 구매업무가 설정돼 있어도 담당자 인계에 걸리는 진행 문서가 있으면 적용을 중단합니다.

## 업데이트

사전 점검이 통과한 동일한 인수로 아래 명령을 실행합니다.

```sh
sudo sh UPDATE_NAS.sh update \
  --development-checker '<개발팀 구매확인자 이름 또는 username:아이디>' \
  --other-checker '<그 외 부서 구매확인자 이름 또는 username:아이디>' \
  --purchaser '<구매 담당자 이름 또는 username:아이디>' \
  --representative '<대표 이름 또는 username:아이디>' \
  --operator admin
```

업데이트는 파일 무결성 확인 → 새 이미지 빌드 → 계정·진행 문서 점검 → 웹 중지 → 기존 데이터·첨부 기준값 저장 → 기존 이미지로 DB·첨부 백업 → DB 변경 → 기존 데이터·첨부 비교 → 기존 직원 계정에 구매 업무 역할 연결·구매 규정 사용 → 앱 검사 → 웹 시작·상태 확인 순서로 진행합니다. 업데이트 중 연차를 재계산하거나 초기 계정·테스트 직원을 생성하지 않습니다. 기존 규정의 검토자 승인완료 권한은 유지하고 새로 자동 부여하지 않습니다.

업데이트 전 백업 이름과 이미지 이름은 기존 설치 폴더에 남습니다. 계정 연결 계획과 비교용 해시는 `data/app/nas-purchase-update-plan.json`에 비공개 권한으로 저장됩니다. 이 파일에는 직원 정보가 포함되므로 외부에 공유하지 마세요. 새 폴더를 그대로 보관하고 예약 백업의 기존 경로는 유지하세요. 예약 백업은 `.current-image`에 기록된 새 이미지를 사용합니다.

## 완료 후 확인

- 기존 직원 로그인·문서함·진행 휴가원/생산 재고 결재·연차·첨부·기존 문서 이력 확인.
- 직원 권한관리에서 네 구매 역할 확인, 구매 규정에서 사용 상태·요청 직급·검토자 승인완료 권한 확인.
- 개발팀 / 그 외 부서 요청이 각 담당자에게 전달되는지, 동일 담당자 승인 시 구매 담당자에게 한 번만 전달되는지 확인.
- 대표 화면의 새 요청 표시·진행 중/완료 분리, 구매 담당자의 결제 완료·반려·보류·집계·엑셀 확인.
- 원래 사용하던 HTTPS 주소에서 로그인·아이디 저장·브라우저 암호 자동입력·알림 확인. 브라우저가 닫힌 상태의 새 푸시 알림은 이번 범위에 포함하지 않습니다.

```sh
sudo sh UPDATE_NAS.sh status
sudo sh UPDATE_NAS.sh logs
```

## 중단·복구

빌드/사전 점검 실패 시 기존 웹은 계속 실행됩니다. 웹 중지 후 백업·DB 변경·보존 비교·계정 연결·앱 상태 검사에서 실패하면 웹을 자동 재개하지 않습니다. 출력 내용을 확인하고, 백업이 만들어져 있다면 다음으로 **이전 이미지와 업데이트 직전 백업을 함께 복구**합니다.

```sh
sudo sh UPDATE_NAS.sh rollback
```

복구는 백업 이후에 입력한 내용을 되돌립니다. 다른 Docker 프로젝트·기존 NAS DB·포트·볼륨은 변경하지 않습니다. `install`, 데이터 폴더 삭제, 초기화용 도구, 임의 DB 복사로 해결하지 마세요. 업데이트 직전 백업 생성 전에 실패했다면 DB 변경은 시작되지 않은 상태입니다. 원인을 확인한 뒤 기존 배포본의 `nas.sh start`로 재개할 수 있습니다.

이 배포 파일에는 회사 DB·비밀번호·실제 직원 명단·가상 직원 생성기·로컬 테스트 실행기·협업일지가 포함되지 않습니다. 실제 NAS의 계정 일치·실행 버전·저장 공간·HTTPS 설정은 현장 사전 점검 결과를 기준으로 판단합니다.
