# NAS 설치 구성 검증 — 2026-10-15

검증 대상은 클라우드의 격리된 Docker 환경이다. 사용자 NAS에는 접속·설치하지 않았고, 기존 PC DB(가상 계정 8개·문서 9개)는 유지했다. 외부 NAS 서비스·MariaDB 계정·자료는 변경하지 않았다.

| 항목 | 결과 |
| --- | --- |
| 이미지 | amd64 Python 3.12.12 / Gunicorn 23 / Django 5.2.18 / MariaDB 10.11.14 |
| 기능 시험 | MariaDB 123건 통과, 제외 없음. SQLite 119건 통과·MariaDB 행 잠금 4건 제외 |
| 실제 동시 처리 | 같은 문서 중복 승인 1회 차감, 동일 직원 다른 휴가 동시 승인 모두 반영, 같은 날짜 동시 제출 중복 거부, 공용연차와 개인 휴가 동시 승인 차감 보존 |
| 빈 운영 설치 | 관리자 1명·문서 0개. 예시 데이터 생성 차단, 임시 암호 자동 생성·첫 로그인 변경, 설치 재실행 시 자료/암호 미변경 |
| 운영 설정 | DEBUG 활성·누락 비밀키·SQLite 운영 설정·와일드카드 허용 주소 모두 시작 거부. 웹 DB 사용자는 전용 계정, 웹 컨테이너에 DB root 암호 없음 |
| 정적 파일 | 해시 CSS·JS·로고·이미지 제공. 일반 계정 및 관리자 로그인 화면 확인 |
| 버전 호환 | Docker Compose 1.29.2 설정 검사·실제 수동 백업 통과. 전체 설치·업데이트 실행은 Docker 28.4 / Compose 2.40.3에서 검증 |
| 백업 | 실 DB dump 및 ZIP/manifest 생성, SHA-256 확인, 예약 일별·월별 생성·자동 정리 범위 시험 |
| 일반 업데이트 | 기존 사용자·직원 정보·암호·문서·연차·알림·감사 이력 유지. 초기 관리자 설정을 덮어쓰지 않음 |
| 스키마 변경·되돌리기 | 시험 전용 테이블을 추가하는 이미지 업데이트 성공. 직전 이미지+DB 백업으로 되돌린 뒤 추가 테이블 제거 및 업무 57레코드 일치 |
| 부분 DDL 실패 | 두 번째 시험 변경에서 일부 테이블 생성 후 의도적 오류. 서비스 중지·일반 시작 거부. rollback 후 추가 테이블 제거·업무 57레코드 일치 |
| 손상 백업·복구 | 잘못된 체크섬 백업 거부·복구 표식으로 일반 시작 제한. 정상 백업 복구 후 변경했던 문서 사유·연차 수치와 전체 업무 자료 일치 |
| PC 화면 | 1280×800, 1366×900, 1920×1080의 홈·문서·일정·복지·직원 권한·백업·규정·내 계정에서 문서 전체 가로 넘침·JS 오류 없음 |

자료 비교는 로그인 시각처럼 시험 중 브라우저 접속으로 정상 변경되는 값을 구분했다. 로그인 검증이 끝난 안정된 시점의 업무 직렬화 자료는 업데이트/복구 후 그대로 일치했다. 계정 암호 해시도 비교에 포함했으며 검증 문서에는 비밀번호·비밀키·원본 DB·전체 레코드를 싣지 않는다.

클라우드 네트워크에는 프록시 CA가 필요해 별도 무시되는 빌드 문맥에서 공개 CA와 프록시 호스트 해석을 추가했다. 원본 NAS Dockerfile의 TLS/패키지 검증은 비활성화하지 않았다. NAS에서는 원본 Dockerfile을 사용한다. 시험 장애를 주입한 마이그레이션과 이미지는 배포 소스에 포함하지 않는다.

화면은 PC 가로 1080px 이상을 기준으로 한다. 768px 태블릿에서는 이 최소 너비에 따른 스크롤이 발생하며 모바일 최적화는 이번 범위가 아니다. 화면 예시는 [로그인](production-login.png), [새 운영 관리자 홈](production-home.png)에서 확인할 수 있다.

실제 NAS 설치·부하·인증서·역방향 프록시·DSM 예약 작업·NAS 외부 백업 인수는 다음 단계다. 초기 HTTP 연결 확인은 HTTPS 정식 운영을 대신하지 않는다. 예약 명령을 시험한 결과와 NAS에서 실제 예약 작업이 설정된 상태는 구분한다.
